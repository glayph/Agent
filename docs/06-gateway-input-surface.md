# ধাপ ০৬ — Gateway / Input-Surface Layer (OpenClaw সমতুল্য: Gateway + Channels)

## লক্ষ্য
এজেন্টের কাছে কাজ/মেসেজ আসতে পারে এমন সব উৎসকে একটা **একক, সামঞ্জস্যপূর্ণ** ইনপুট ফরম্যাটে
রূপান্তর করা, যাতে "কোথা থেকে এলো" থেকে "কীভাবে প্রসেস হবে" — এই দুটো আলাদা থাকে।

## OpenClaw-তে এটা যেভাবে কাজ করে
- একটা একক Gateway প্রসেস, যার মধ্যে সব "channel" (WhatsApp/Telegram/Discord/Slack ইত্যাদি)
  ঢুকে ইনবাউন্ড মেসেজ পাঠায়।
- Gateway প্রতিটা ইনবাউন্ড মেসেজকে একটা কমন ফরম্যাটে নরমালাইজ করে, কোন সেশন/এজেন্টের সাথে সম্পর্কিত
  তা নির্ণয় করে, তারপর এজেন্ট কোরের কাছে হ্যান্ডঅফ করে।

## OwlClaw-এর জন্য পুনর্গঠন — "channel" ≠ শুধু চ্যাট অ্যাপ
আপনার প্রেক্ষাপটে "channel"-কে সাধারণীকরণ করে **"input surface"** ভাবুন। এটা হতে পারে:
- CLI কমান্ড
- Antigravity IDE থেকে আসা একটা কমান্ড/ইভেন্ট
- একটা internal task-queue API কল
- একটা webhook
- (ভবিষ্যতে চাইলে) সত্যিকারের চ্যাট চ্যানেল

## আপনার OwlClaw-তে কী তৈরি করতে হবে
1. একটা কমন `InboundEvent` স্কিমা:
   ```json
   {
     "surface": "cli | ide | task_api | webhook | ...",
     "session_key": "string",
     "payload": {"text": "...", "attachments": [...]},
     "timestamp": "...",
     "sender_meta": {"...": "..."}
   }
   ```
2. প্রতিটা input surface-এর জন্য একটা adapter ইন্টারফেস: `normalize(raw) -> InboundEvent`।
   নতুন surface যোগ করা মানে শুধু একটা নতুন adapter লেখা, কোর লজিক না ছোঁয়া।
3. একটা `session_key` নির্ণয়ের নিয়ম — সাধারণত `surface + conversation/thread-id + agent-role`-এর
   সমন্বয়ে, যেহেতু ধাপ ০৭-এর queue system এই session_key দিয়েই সিরিয়ালাইজেশন করবে।
4. একটা single entry-point ফাংশন (`ingest(raw_event, surface_id)`) যা সব adapter-এর আউটপুট
   পরবর্তী ধাপ (queue)-এ পাঠায় — কোথাও যেন সরাসরি এজেন্ট-কোর কল না হয় adapter থেকে বাইপাস করে।

## Behavior Contract
1. প্রতিটা নতুন input surface শুধু একটা নতুন adapter যোগ করে সাপোর্ট করা যাবে, কোর কোড না বদলিয়ে।
2. একই `session_key`-নির্ণয় লজিক সব surface জুড়ে সামঞ্জস্যপূর্ণ।
3. Normalize না হওয়া raw ইভেন্ট কখনো সরাসরি এজেন্ট-কোরে পৌঁছাবে না।

## Acceptance Criteria
- [ ] দুইটা ভিন্ন dummy surface (যেমন CLI ও একটা fake webhook) একই `InboundEvent` ফরম্যাট আউটপুট দেয়।
- [ ] `session_key` নির্ণয় ইউনিট-টেস্টে ডিটারমিনিস্টিক প্রমাণিত।
- [ ] নতুন surface যোগ করার সময় কোর agent লজিকের কোনো ফাইল পরিবর্তন করতে হয় না।

## যাচাই ও সংশোধন প্রোটোকল
00-README.md-এর Universal Protocol অনুসরণ করো। বিশেষভাবে:
- খুঁজে দেখো OwlClaw-তে বর্তমানে ইনপুট কীভাবে ঢোকে (সম্ভবত সরাসরি CLI/ফাংশন কল হিসেবে, কোনো
  normalize স্তর ছাড়া) — সেটাকে ভেঙে না ফেলে, একটা adapter হিসেবে wrap করো, যাতে existing
  ব্যবহার পদ্ধতি অপরিবর্তিত থাকে কিন্তু ভেতরে এই কমন ফরম্যাটে যায়।

## নির্ভরতা
স্বাধীন, কিন্তু ধাপ ০৭ (command queue) এটার output-এর উপর সরাসরি নির্ভর করে।

## এই ধাপ শেষে যা থাকা উচিত
একটা সামঞ্জস্যপূর্ণ ইনপুট-নরমালাইজেশন স্তর, যেকোনো নতুন সোর্স থেকে কাজ ঢোকানো সহজ করে তোলে।
