# ধাপ ০৮ — Heartbeat System (OpenClaw সমতুল্য: Heartbeat)

এটাই "২৪/৭ active" থাকার আসল মেকানিজম — আপনার মূল প্রশ্নের প্রথম অংশ।

## লক্ষ্য
ব্যবহারকারীর কোনো ইনপুট ছাড়াই, একটা নির্দিষ্ট বিরতিতে এজেন্ট নিজে থেকে জেগে উঠে পূর্বনির্ধারিত
চেকলিস্ট চালাবে, এবং প্রয়োজনে proactively কিছু করবে বা জানাবে।

## OpenClaw-তে এটা যেভাবে কাজ করে
- Gateway প্রতি N মিনিটে (ডিফল্ট প্রায় ৩০) একটা heartbeat cycle ট্রিগার করে।
- সাইকেল: টাইমার ফায়ার → একটা `HEARTBEAT.md`-জাতীয় ফাইল পড়ে → তাতে লেখা instructions execute
  করে → ফলাফল প্রয়োজনে একটা চ্যানেলে পাঠায় → আবার ঘুমিয়ে পড়ে।
- এজেন্ট প্রতিটা heartbeat-এ একটা রেসপন্স টাইপ বেছে নেয়: কিছু করার নেই (no-op), proactive
  মেসেজ পাঠানো, নীরবে টুল/কমান্ড চালানো, বা মেমরি আপডেট করা।
- `quiet_hours` কনফিগার করা যায় (যেমন রাতে হার্টবিট বন্ধ)।
- খরচ নিয়ন্ত্রণে হার্টবিটের জন্য একটা সস্তা মডেল ব্যবহারের সুপারিশ থাকে (ধাপ ০৩-এর `heartbeat` lane)।
- ম্যানুয়ালি একটা হার্টবিট সাইকেল অবিলম্বে ট্রিগার করা এবং একটা dry-run (আসলে এক্সিকিউট না করে শুধু
  কী হতো তা দেখানো) মোডও থাকে, টেস্টিং-এর জন্য।
- Heartbeat, Cron (ধাপ ০৯)-এর থেকে আলাদা: হার্টবিট হলো ব্যাচড, পর্যায়ক্রমিক, সাধারণ চেক-আপ;
  cron হলো নির্দিষ্ট সময়ে, নির্দিষ্ট একটা কাজের সুনির্দিষ্ট সিডিউল।

## আপনার OwlClaw-তে কী তৈরি করতে হবে
1. `workspace/HEARTBEAT.md` (বা রোল-ভিত্তিক: `workspace/agents/<role>/HEARTBEAT.md`) — প্রতিটা
   লাইনে একটা প্রোঅ্যাকটিভ চেক-টাস্ক, যেমন: "Antigravity IDE-এর টাস্ক-কিউতে আটকে থাকা কাজ আছে
   কিনা দেখো", "Verifier কোনো unresolved ইস্যু ফ্ল্যাগ করেছে কিনা দেখো", "গত রানের কোনো ব্যর্থ
   বিল্ড/টেস্ট আছে কিনা দেখো"।
2. একটা asyncio/APScheduler-ভিত্তিক scheduler যেটা কনফিগারযোগ্য ইন্টারভালে ফায়ার করে।
3. প্রতিটা heartbeat রান ধাপ ০৭-এর `TaskQueue`-তে একটা আলাদা **`heartbeat` lane**-এ enqueue হবে —
   **কখনো ব্যবহারকারীর সক্রিয় (main lane) সেশনকে interrupt করবে না**। যদি main lane ব্যস্ত থাকে,
   হয় heartbeat শুধু read-only চেক করবে (কোনো shared state না ছুঁয়ে), অথবা পরের সাইকেল পর্যন্ত অপেক্ষা করবে।
4. `quiet_hours` কনফিগ (শুরু/শেষ সময়, টাইমজোন)।
5. ধাপ ০৩-এর `heartbeat` lane থেকে ডিফল্টভাবে সস্তা মডেল ব্যবহার করবে।
6. একটা ম্যানুয়াল ট্রিগার ফাংশন/কমান্ড (`run_heartbeat_now(dry_run=False)`)।
7. রেসপন্স টাইপগুলো OwlClaw-এর প্রেক্ষাপটে ম্যাপ করো: no-op / proactive-notify (যেমন একটা লগ বা
   IDE নোটিফিকেশন) / silent-tool-run (ধাপ ০৪-এর ToolGate দিয়ে) / memory-update (ধাপ ০২)।

## Behavior Contract
1. হার্টবিট নির্ধারিত ইন্টারভালে, ব্যবহারকারীর কোনো ইনপুট ছাড়াই, নিজে থেকে ফায়ার করে।
2. `quiet_hours`-এর মধ্যে হার্টবিট চলবে না।
3. হার্টবিট কখনো একটা সক্রিয় main-lane রানকে বাধাগ্রস্ত/corrupt করবে না।
4. ম্যানুয়াল ট্রিগার ও dry-run মোড উপলব্ধ, প্রোডাকশনে না চালিয়েও টেস্ট করা যায়।

## Acceptance Criteria
- [ ] নির্ধারিত ইন্টারভালে হার্টবিট ফায়ার করে, লগে দৃশ্যমান।
- [ ] `quiet_hours`-এর মধ্যে সেট করা সময়ে হার্টবিট suppress হয়।
- [ ] একটা main-lane টাস্ক চলাকালীন হার্টবিট সাইকেল ফায়ার করলে সেই টাস্কে কোনো প্রভাব পড়ে না
      (টেস্টে প্রমাণিত — main টাস্কের আউটপুট/state অপরিবর্তিত থাকে)।
- [ ] `run_heartbeat_now(dry_run=True)` আসলে কিছু এক্সিকিউট না করেই কী হতো তা রিপোর্ট করে।

## যাচাই ও সংশোধন প্রোটোকল
00-README.md-এর Universal Protocol অনুসরণ করো। বিশেষভাবে:
- যদি OwlClaw-এ ইতিমধ্যে কোনো "polling loop" বা "watcher" থাকে যা informal ভাবে একই কাজ করার
  চেষ্টা করে, সেটাকে এই heartbeat lane-এ migrate করো, এবং নিশ্চিত করো migration-এর পর সেটা আর
  main lane-এর সাথে collide করছে না।
